# 本地代理：服务、规则与请求列表

rDevTool 的 **本地代理** 用于在本机建立一个可复用的 HTTP/HTTPS 入口，把项目、浏览器、命令行或其他本地应用的请求交给同一个代理 profile 处理。代理页把服务状态、规则配置、实际请求和规则诊断放在同一个工作流里。

这篇文档重点说明：

1. 服务 profile 如何创建、启动、停止和判断进程归属。
2. 规则如何匹配请求，以及转发、Mock、阻断分别怎么配置。
3. 请求列表如何搜索、筛选、查看详情、清理和自动刷新。
4. “诊断规则”与“真实请求记录”有什么区别。
5. 代理如何绑定项目运行档案、Link 和工作区，并安全地导入导出。

## 1. 先理解代理页的三层数据

| 层级 | 回答的问题 | 页面位置 |
| --- | --- | --- |
| 服务 profile | 请求从哪个本地地址进入，谁在监听 | 左侧服务列表、代理配置 |
| 规则 | 请求满足哪些条件时做什么 | 右侧规则列表、规则配置 |
| 请求事件 | 实际发生了什么，响应是什么 | 请求面板、请求详情 |

还有一个只读的 **诊断结果**：它根据当前配置模拟一个请求，告诉你会命中哪条规则、哪些条件没有满足，以及端口是否正在监听。诊断不是网络请求，也不会产生请求事件。

代理是否真正可用，至少要同时满足：

1. 选中的 profile 配置完整。
2. 监听地址和端口属于预期的代理服务。
3. 代理服务状态为 **运行中**，且不是外部进程占用。
4. 目标请求确实进入了该 profile。
5. 请求命中的规则、上游地址和最终响应符合预期。

只看到端口存在，或者只看到服务状态为运行中，都不能证明业务请求已经走通。

## 2. 代理页概览

从左侧打开 **本地代理**。顶部概览栏显示当前配置源和范围内的统计：

- **服务**：当前配置源中的 profile 数量。
- **运行中**：由 rDevTool 管理且正在监听的 profile 数量。
- **外部占用**：端口正在监听，但进程不是 rDevTool 管理的数量。只有出现外部占用时才显示。
- **规则**：当前选中 profile 的规则数量。
- **请求**：当前选中 profile 已记录的请求事件数量。

顶部有两个主要入口：

- **请求记录**：打开请求列表和诊断面板。
- **代理配置**：管理配置源、服务 profile、导入导出和服务字段。

页面主体分成左右两栏：左侧是服务，右侧是当前服务的规则。收起左侧服务列表后，右侧可以获得更多规则空间；收起状态只保存在当前本机界面偏好中，不会修改代理配置。

## 3. 服务 profile

### 3.1 服务卡片显示什么

每个服务卡片包含：

- 服务名称。
- 实际监听 URL，例如 `http://127.0.0.1:8787`。
- 当前状态。
- 规则数量和请求数量。
- 启动或停止按钮。

点击卡片主体会切换当前 profile，右侧规则列表和顶部规则/请求计数随之刷新。卡片上的请求数量只属于该 profile，不是所有代理服务的总和。

### 3.2 服务状态

| 状态 | 含义 | 处理建议 |
| --- | --- | --- |
| 已停止 | 当前没有检测到该 profile 的监听服务 | 点击启动，或先检查地址和端口 |
| 运行中 | 端口正在监听，且进程由 rDevTool 管理 | 可以把项目或命令行指向监听 URL |
| 外部占用 | 端口正在监听，但不是 rDevTool 创建的进程 | 先确认 PID、命令和工作目录，不要直接停止 |
| 需要重启升级 | 服务版本与当前应用不一致 | 停止后重新启动，让服务升级 |
| 未保存 | 代理配置弹窗中的新服务草稿 | 先保存服务，保存前不会产生可用监听入口 |

**外部占用** 是风险状态，不是“已经启动”。rDevTool 不会通过停止按钮结束外部进程；需要由使用者确认进程归属，或者给 rDevTool profile 换一个空闲端口。

### 3.3 新建服务

可以从页面底部 **新建服务**，或打开 **代理配置 > 新建服务**。填写：

| 字段 | 说明 |
| --- | --- |
| 名称 | 给人看的 profile 名称，例如 `项目 A 联调`、`Mock API` |
| 监听地址 | 代理服务绑定的本机地址，常见是 `127.0.0.1` |
| 端口 | 本机监听端口。不要与其他服务或项目端口冲突 |
| 上游地址 | 可选的默认目标基地址；相对路径请求会拼接到这里 |
| 上游代理 | 可选的默认 HTTP/SOCKS 出站代理 |
| 记录正文 | 是否保存请求和响应的 Body 预览 |
| 正文预览字节 | 每个请求/响应最多保存的 Body 预览大小 |

保存服务只写入配置，不会自动启动监听。保存后回到服务卡片点击启动，并刷新状态。

### 3.4 默认转发与出站代理

服务的 **默认转发** 处理没有被规则改写的请求：

- 填写上游地址时，相对路径可以拼接到该基地址。
- 上游地址为空时，按请求本身的原始目标转发。
- 填写上游代理时，规则选择“继承默认”会使用该代理。
- 默认上游代理为空时，继承默认通常直连。

服务默认转发只决定默认目标和默认出站方式，不会让所有请求自动命中某条规则。规则中的出站设置可以覆盖服务默认值。

### 3.5 通过环境变量接入

代理配置中会显示当前监听 URL 对应的 `HTTP_PROXY` 和 `HTTPS_PROXY` 复制按钮。可以把它们复制到终端或项目启动档案，让命令行工具通过该入口发请求。

使用环境变量时要注意：

- 这只改变请求经过的代理入口，不会替代项目自身的 API Base URL。
- 工具是否遵守 `HTTP_PROXY`/`HTTPS_PROXY` 取决于工具实现。
- 需要绕过代理的地址应使用工具自己的 No Proxy 机制或项目运行配置。
- 代理 URL、上游 URL 和请求 Header 可能包含敏感信息，不要直接提交到仓库。

## 4. 规则匹配

右侧规则列表属于当前选中的服务。每条规则显示名称、动作、出站策略、优先级、可选延迟、方法和匹配目标。

### 4.1 规则字段

打开 **新规则** 或点击已有规则进入 **规则配置**：

| 字段 | 行为 |
| --- | --- |
| 规则名称 | 用于列表、诊断和请求详情显示 |
| 优先级 | 数值越小越先参与匹配；同优先级再按名称和 ID 稳定排序 |
| 方法 | 可选 `GET`、`POST`、`PUT`、`PATCH`、`DELETE`、`OPTIONS`；留空表示任意方法 |
| 路径前缀 | 请求路径必须以该值开头，例如 `/api` |
| URL 包含 | 完整 URL 必须包含该字符串 |
| Header 名 | 可选的请求 Header 名称 |
| Header 包含 | Header 存在时，其值必须包含该字符串；留空只检查 Header 是否存在 |
| 动作 | `转发`、`Mock` 或 `阻断` |
| 启用 | 关闭后规则会保留，但不会参与匹配 |
| 延迟 ms | 对应动作增加的模拟延迟，适合复现慢请求 |

多个条件同时存在时是 **AND** 关系：方法、URL、路径和 Header 都满足，规则才算命中。空条件表示不限制该项。

### 4.2 优先级和更具体的规则

代理会按优先级从小到大评估规则，命中第一条启用的规则后采用该动作。常见写法是：

```text
P10  GET  /api/health       -> Mock 200
P20  GET  /api              -> Forward
P30  任意  /                 -> 默认转发
```

更具体的 `/api/health` 应该使用更小的 priority。诊断发现“更具体的规则也能命中，但排在已命中规则之后”时，会显示规则被遮蔽的警告；调整优先级后重新诊断。

### 4.3 启用和批量开关

规则列表右上角的 **启用** 和 **停用** 会批量切换当前 profile 的规则。单条规则右侧的开关只修改该条规则。

停用规则不会删除它的配置，也不会清除历史请求。适合临时关闭 Mock 或阻断规则，验证真实上游后再恢复。

保存规则后，代理页会刷新规则列表。已经发生的请求不会因为规则修改而回写；要验证新配置，必须重新发起请求。

## 5. 三种规则动作

### 5.1 转发

转发规则把请求交给目标上游，可以配置：

- **转发到**：覆盖请求的目标基地址；为空时使用原请求地址或服务默认上游。
- **路径改写**：修改转发路径前缀，例如把 `/debug-api` 改写到 `/api`。
- **出站策略**：
  - **继承默认**：使用服务的上游代理；没有服务代理时直连。
  - **直连**：这条规则不使用任何上游代理。
  - **指定代理**：只对这条规则使用指定 HTTP/SOCKS 代理。
- **追加请求 Header**：以 `Header: value` 形式填写需要追加的请求头。
- **追加响应 Header**：填写返回给调用方前追加的响应头。
- **延迟**：模拟转发耗时。

“转发到”只决定请求目标，不决定请求是否经过上游代理；出站策略单独控制这一点。

### 5.2 Mock

Mock 规则不访问上游，直接返回配置好的响应：

- 状态码，例如 `200`、`404` 或 `500`。
- `Content-Type`。
- 响应 Header。
- 响应正文。
- 可选延迟。

适合模拟接口成功、空数据、权限失败、慢响应和异常响应。Mock 命中的请求在请求列表中显示 `Mock` 动作，并且请求/响应正文是否可见还受服务的 **记录正文** 开关影响。

### 5.3 阻断

阻断规则不访问上游，直接返回配置好的状态码和阻断响应正文。适合验证前端在接口不可用、接口被拒绝或权限异常时的行为。

阻断与 Mock 的区别是意图：Mock 表示“用本地响应替代上游”，阻断表示“明确拒绝这类请求”。请求列表会分别显示 `Mock` 和 `阻断`，筛选与诊断也会保留这个动作类型。

## 6. 请求列表

点击顶部 **请求记录** 打开当前 profile 的请求面板。请求列表只显示当前选中服务的事件，不会把其他 profile 的流量混在一起。

### 6.1 自动刷新和数量

当选中的 profile 正由 rDevTool 管理并处于运行中时，请求面板打开后会自动刷新，刷新间隔约为 2.5 秒。切换到其他应用或页面不可见时会暂停可见刷新，回到页面后继续。

顶部显示 `可见 / 总数`：

- 初始最多加载 50 条符合当前条件的事件。
- 向下滚动或点击 **下滑加载更多** 才会继续加载。
- “总数”是当前搜索和筛选条件下的数量，不一定等于服务累计事件总量。
- **刷新**会重新读取持久化的请求记录。
- **清空**会清除当前 profile 的请求事件，不会删除服务或规则。

### 6.2 搜索和筛选

搜索框匹配以下内容：

- HTTP 方法。
- 完整 URL 和路径。
- 状态码。
- 动作类型，例如 `Mock`、`转发`、`阻断`。
- 命中的规则名称。
- 代理 profile 名称和错误信息。

筛选选项：

| 筛选 | 含义 |
| --- | --- |
| 全部 | 当前 profile 的所有事件 |
| 成功 | 没有错误且状态码为 2xx/3xx |
| 失败 | 错误、4xx/5xx、错误动作 |
| Mock | 被 Mock 规则处理 |
| 转发 | 走转发、隧道或默认转发的请求 |
| 阻断 | 被阻断规则处理 |

搜索和筛选可以组合。点击 **重置** 清除搜索词并恢复“全部”。

### 6.3 请求行和详情

请求行显示方法、状态码、动作、时间和路径。颜色用于快速扫描，但最终判断应打开详情：

- 状态码、耗时。
- 请求和响应字节数。
- 完整 URL。
- 命中的规则和动作。
- Request Headers。
- Response Headers。
- Request Body 预览。
- Response Body 预览。
- 错误信息和正文是否被截断。

服务关闭 **记录正文** 后，Header 和基础信息仍会记录，但 Body 预览不会保存。开启正文记录后也会受到“正文预览字节”上限限制，界面显示带 `+` 的 Body 标题时，表示内容可能被截断。

请求记录适合回答“实际发生了什么”；不要只根据规则列表推断请求已命中。

## 7. 请求诊断

请求面板的诊断区可以选择 HTTP Method，填写路径或完整 URL，并点击 **诊断**。也可以先选中一条真实请求，再点击 **使用选中请求** 自动带入方法和路径。

诊断结果会显示：

- profile 名称、监听 URL 和端口是否正在监听。
- 规范化后的请求方法、URL、路径和 Header 数量。
- `已命中`、`规则命中但端口未监听` 或 `未命中`。
- 最终命中的规则、priority 和动作。
- 每条规则的逐项判断：是否启用、方法、URL、路径和 Header 是否满足。
- 没有启用规则、没有命中规则、具体规则被遮蔽等警告。

### 7.1 路径和完整 URL怎么填

- 填 `/api/health` 时，代理会使用服务的上游地址作为诊断基地址；没有配置时使用诊断用的本地占位基地址。
- 填 `https://api.example.com/health` 时，直接按完整 URL 诊断。
- 相对路径依赖服务上游地址或请求 Header 中的 Host；配置不完整时会提示目标无效。
- 诊断使用输入的 Header 条件，但不会发送这些 Header 到真实服务器。

### 7.2 诊断和真实请求的区别

| 项目 | 规则诊断 | 请求记录 |
| --- | --- | --- |
| 是否发出网络请求 | 否 | 是，来自真实客户端 |
| 是否产生请求事件 | 否 | 是 |
| 能否看到真实响应 | 否 | 能看到状态、Header 和可选 Body |
| 用途 | 检查配置和匹配条件 | 验证实际链路和上游结果 |
| 是否证明端口可用 | 只报告当前监听状态 | 记录请求是否真正进入服务 |

推荐先诊断，再用真实客户端发起一次验证请求，最后在请求详情中确认上游、Mock 或阻断结果。

## 8. 配置源、工作区和项目绑定

代理配置顶部显示当前 **配置源** 和代理配置文件路径。切换配置源前必须保存或取消当前服务、规则和导入草稿；有未保存改动时，页面会阻止切换。

代理范围跟随当前工作区：

- `system` 全局视图用于查看所有共享 profile。
- 普通工作区只显示纳入当前范围的 profile。
- 从工作区移除 profile 不会删除配置源中的服务。
- 修改共享 profile 会影响引用它的其他工作区，保存前应核对工作区和配置源。

项目启动档案可以绑定本地代理 profile。绑定后，运行面板的链路预检会检查 profile 是否存在、配置源是否可用、端口是否监听以及是否被外部进程占用。项目启动异常时，应同时查看 Runtime Panel 和本地代理的请求记录。

项目启动档案、运行配置和运行面板的完整说明见 [项目启动与运行面板](project-runtime.md)。

Link 可以把启动代理、启动项目、打开页面和验证请求编排成一条链。Link 负责步骤顺序；代理页负责 profile、规则和请求证据。

## 9. 导入和导出代理包

在 **代理配置** 中：

- **导入**选择 `.json` 代理包。导入会创建一个新的代理服务，把包内规则归属到新服务，不覆盖现有服务。
- **导出选中**把当前服务配置、规则、追加 Header、Mock Body 和上游地址写入 `.rdevproxy.json`。

导入后要检查名称、监听地址和端口，避免和本机已有服务冲突。导出前必须检查：

- 上游地址是否包含内网域名或临时环境信息。
- 上游代理是否带有用户名、密码或私有地址。
- Request/Response Header 是否有 Cookie、Authorization 或内部 Header。
- Mock Body 是否包含业务数据。

代理包是配置迁移文件，不是凭据保险箱。分享前先脱敏，团队成员导入后仍要按本机端口和网络环境重新验证。

## 10. 常见排障流程

### 端口显示外部占用

打开服务状态详情，确认监听 URL、PID/进程归属和命令。不要直接停止未知进程；可以确认它属于本次项目后再处理，或者把 rDevTool profile 改到空闲端口。修改端口后同步更新项目启动档案、Runtime Profile 和 Link。

### 服务运行但请求列表没有记录

1. 确认客户端真的使用了 profile 的监听 URL。
2. 确认当前选中的是产生请求的 profile。
3. 关闭搜索和筛选，点击刷新。
4. 检查客户端是否绕过了 `HTTP_PROXY`，或者使用了自己的代理配置。
5. 检查请求是否在代理服务之前就失败，例如 DNS、TLS 或客户端连接错误。

### 请求进入了但没有命中规则

先使用选中请求进行诊断，查看方法、完整 URL、路径和 Header 条件。重点检查路径前缀是否带 `/`、URL 包含条件是否匹配完整 URL、Header 名大小写和 Header 值是否正确，以及规则是否已经启用。

### 命中了错误的规则

检查 priority 和更具体的规则是否排在前面。诊断中的“具体规则被遮蔽”警告表示有更长路径前缀的规则也能匹配，但当前规则优先级更高。将更具体的规则设置为更小的 priority 后重新验证。

### Mock 或阻断没有生效

确认请求实际进入 profile，并检查规则动作、启用状态、方法和路径。更新规则后必须重新发请求；已有请求记录不会自动重新计算。

### 请求详情没有 Body

检查服务配置里的 **记录正文** 是否开启，以及正文预览字节上限是否足够。关闭正文记录后，Header 和基础信息仍然存在，这是有意的隐私和性能边界。

### 转发目标正确但上游访问失败

分别检查转发目标、服务默认上游、规则出站策略和指定上游代理。`继承默认`、`直连`、`指定代理` 是三个独立选择；不要只改上游地址而忽略出站策略。

## 11. CLI 对照

桌面界面不可用时，可以用 CLI 做只读检查或执行明确的 profile 操作。`<profile>` 使用 profile Key 或名称；写入操作前先看当前配置源和状态。

```bash
# 查看配置文件、profile 和当前状态
rdevtool --json proxy source
rdevtool --json proxy list
rdevtool --json proxy status
rdevtool --json proxy show <profile>

# 启动、停止和重启 profile
rdevtool --json proxy start <profile>
rdevtool --json proxy stop <profile>
rdevtool --json proxy restart <profile>

# 查看规则和预测一次请求的匹配结果
rdevtool --json proxy rule-list --profile <profile>
rdevtool --json proxy diagnose --profile <profile> --method GET --url /api/health
rdevtool --json proxy verify --profile <profile> --url /api/health

# 将 profile 与项目运行能力绑定
rdevtool --json proxy bind-runtime --profile <profile>
```

`diagnose` 是规则预测，`verify` 会进一步验证代理链路。命令输出中的 configured、requested 和 observed 状态要区分阅读：配置存在不等于端口监听，端口监听也不等于真实业务请求成功。

## 12. 安全和记录建议

- 本地代理主要用于联调、Mock、阻断和可复核的请求排查，不要把它当成生产网关。
- 共享配置前清理 Cookie、Authorization、私有 Header、代理认证和内网地址。
- 记录正文只在确有需要时开启，问题复现后及时关闭或清空请求记录。
- 代理日志和请求 Body 可能包含业务数据，不要直接提交到仓库或复制到公共工单。
- 每次排障记录 profile、监听 URL、配置源、规则名称、请求路径和诊断结果，方便后续写入知识库。
